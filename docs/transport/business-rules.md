# 客货邮业务规则（硬约束）

> 这份文档是**产品前提**，所有调度、路径、审核、可视化的实现都必须服从这里的规则，不能为了"看起来更聪明"而违背。

## 1. 我们用的是公交/大巴的**空闲运力**

- 司机的本职工作是**按自己所属线路，从起点站开到终点站**；
- 我们的取货 / 派货 / 联运，都只是**顺路捎带**，不能改变"司机按线路跑"这个本职；
- 因此：**线路上每一个站点都会停靠**，不会因为某个订单跳过站点；
- 允许的偏离只有一种：**按订单做小范围绕行**（绕行距离/时长有上限，超出就判定"成本过高"）。

对应实现：

- `DeterministicScheduleSimulator`：车辆位置完全按线路站序 + 计划分钟推进，逐站停靠；
- `transport_dispatch_plan_item.detour_distance_km / detour_duration_seconds / service_point_station_id`
  记录"相对公交骨架的绕行代价"，骨架站为 0；
- `MultiLegPlanner` 的换乘/绕行惩罚（`DETOUR_PENALTY_MINUTES_PER_KM` 等）保证不会为了单个订单大幅绕行。

## 2. 一个班次 = 一个往返（去程 + 返程）

- 去程：起点站 → 终点站，逐站停靠，途中取货/派货；
- **返程：终点站 → 起点站，逆向再来一遍**，站点同样逐个停靠，**同样可以取货/派货**；
- 因此班次时长按"往返"配置（`transport_shift.planned_duration_minutes` ≈ 线路单程分钟的 2 倍）。

对应实现：`DeterministicScheduleSimulator.compute()` 在 `elapsed > 单程时长` 后进入返程阶段
（位置 = 去程在折回时刻的位置，但当前站/下一站方向相反），往返跑完后收车回起点站。

## 3. 不是所有订单都要接（可以选择不入池）

判断标准：**过于遥远 / 不可达 / 成本高** 的订单，宁可不接，也不要让一辆公交跨城空跑。

- 承运审核（下单时自动执行）会给出：通过 / 需客户操作 / 需人工确认 / 拒运；
- 只有**审核通过**的订单才会进入"待入池"，再由调度员归集入池参与调度；
- 距离过远（默认起讫直线 > ~35km，即路网约 45km）→ 转人工确认，不自动入池。

对应实现：`CargoReviewServiceImpl`（`MAX_SERVICE_KM`、`ROAD_UNREACHABLE`、`DETOUR_TOO_LARGE` 等规则码）
+ `DispatchServiceImpl.collectOrders`（只归集 `READY_FOR_POOL` 状态的订单）。

## 4. 审核结论的表达方式：有办法就告诉用户做什么，没办法就说明为什么不能运

- **有解决方案** → 「需您操作」：明确告诉用户做什么（例如"把货物送到就近站点 X 交接"、
  "拆分为 ≤30kg 的多件"、"该单需换乘联运，请按提示到换乘站交接"）；
- **没有解决方案** → 「无法运输 / 拒运」：明确说明原因（禁运品、危险品、超重且无法拆分、
  当前公交线网无法覆盖等）。

对应实现：后端只返回 `reviewStatus + reviewReasonCodes(+ message)`，
前端 `miniprogram/utils/review.js` 统一映射文案，`send.js` 的 `_servicePointHint` / `_checkStationAccess`
给出"送到哪个站点 / 一键改用就近站点"的操作入口。

## 5. 联运必须统筹时间，换乘站过远要留足交接时间

- 跨片区订单**不能由一台车从头跑到尾**：相邻段要换成"当前就在下一段起点附近"的车/司机；
- 交接需要时间：换乘站越远，越要为"新车从当前位置开到换乘站"留时间，再叠加交接作业时间；
- 因此每段的预计出发时间 = 上一段到达时间 + 交接停留 + 新车调动（行驶）时间。

对应实现：

- `MultiLegServiceImpl.relayFarLegsToNearbyVehicles()`：第 2 段起按"谁离本段起点近"改派，
  当前车离本段起点 >6km 且换车能近 3km 以上才改派，并把前一段标记为需要换乘交接；
- `retimeWithReposition()`：改派后按"上一段到达 + 交接停留(`HANDOVER_DWELL_MINUTES`) + 新车调动时间"重排各段时间。

## 6. 演示与验收口径

- 附近公交 / 实时公交展示的车辆**必须跑在真实公交线路上**（347 路区间、320 路、329 路、349 路…），
  位置由班次计划推算（无真实 GPS 时明确标注"位置推算"），不伪造真实上报；
- 调度可视化应能一眼看出**哪条线是哪台车**（每车一色 + 车辆配色图例 + 行驶方向箭头 + 经停序号）；
- 多段联运要在可视化里写清：**哪个订单、在哪一站、交给哪位司机/转运站点工作人员**。
