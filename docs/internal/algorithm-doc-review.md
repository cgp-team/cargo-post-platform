## 两份原始文档的定位

- 《路径规划模型数据与参数规范》：实验模型说明书，按"固定输入 / 可调参数 / 求解输出"三层定义模型。固定输入为玩具级数据集（场站 S0 + 站点 S1–S9 的二维坐标，欧氏直线距离），两类订单场景（超载混合单、3 组标准单车次订单），硬约束为载客 ≤ 5 人、载货 ≤ 4 件、乘客先上车后下车；可调参数为蚁群算法（ACO）全套超参数与多车分区并行调度配置；输出为闭环路径、里程、分配明细、方案对比与可视化图表。结论已给定：超载场景最优为双车分区并行，总里程 51.332。
- 《客货邮软件功能故事型》：叙事体产品功能故事，以调度员一个晚高峰的完整流程（订单归集 → 约束校验 → ACO 双车规划 → 一键下发 → 实时监控 → 静态分批 → 返程结算 → 下一周期）描述软件期望行为，使用与规范文档相同的场景 1 数据和结果。

两份文档是算法组的实验模型定义与产品愿景描述。故事稿存在几处与自身分配方案矛盾的细节（如一号车"S3 接乘客 5"、二号车"S6 接乘客 4"），可作为产品流程参考，不可作为数据依据。

## 初版差异对照清单（历史记录）

| 维度 | 仓库对接契约（旧） | 算法组两份文档 |
|---|---|---|
| 接口形态 | 异步任务 API：提交快照 → 轮询状态 → 取结果 | 未提接口，只有"输入 → ACO → 输出"的实验流程 |
| 坐标与距离 | 真实经纬度，坐标系待确认（WGS84/GCJ-02） | 抽象二维坐标，欧氏直线距离 |
| 路网 | 有 `roadNodeId`/`roadEdgeId`，路网格式与更新待确认 | 无路网概念，任意两点直连 |
| 时间 | ISO 8601 带时区；订单有最早取货/最迟送达时间窗；车辆有后续站点 ETA | 输入无时间窗；仅故事稿出现预计到达时间 |
| 调度模式 | `rollingWindowMinutes` 暗示滚动窗口 | 静态分批、批次锁定，临时加单明确进下一批次、不重规划 |
| 车辆模型 | 有班次 ID、当前位置、状态、后续站点 ETA | 只有容量上限，一律从场站 S0 闭环出发 |
| 订单模型 | 类型、取送节点、件数、重量、体积、优先级、时间窗 | 只有乘客（上/下车站）、派送（站点）、揽收（站点），每件数量为 1 |
| 容量约束 | 当前载客量 + 剩余货运容量（数值型） | 硬上限 5 人 / 4 件，按件数不按重量体积 |
| 求解算法 | 契约不限定，只要求返回算法/参数版本 | 明确只用蚁群 ACO，给出全套超参数 |
| 多车策略 | 未规定 | 超载时唯一采用多车同时段分区并行 |
| 结果校验与审核 | 业务后端校验 + 人工审核后才落库 | 模型自带时序/超载校验；故事稿中调度员直接确认，无审核流 |
| 幂等/重试/错误码 | requestId 幂等、退避重试、错误码分类（待确认） | 未提 |
| 降级策略 | 算法不可用时回退手工/模拟派单 | 仅有"扫码失败手动确认"的业务兜底，无算法降级 |
| 输出指标 | 评分、额外里程、乘客延误、预计收入、预计成本 | 仅里程为定量；成本为定性四维评估，无收入/延误量化 |
| 可视化 | 契约未涉及 | 要求站点散点图、单车闭环图、多车对比图 |

## 算法组逐条回复结论（2026-08-09 收到）

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 坐标与路网 | 真实经纬度 + 高德路网；编程组暂时拿不到路网可先做两点直线距离，后续算法组配合改造适配路网 |
| Q2 | 坐标系 | 由编程组决定，建议统一 GCJ-02；转换由编程组在调用算法前完成（GPS/北斗为 WGS-84，与 GCJ-02 有偏移） |
| Q3 | 多维容量与优先级 | 仅按件数约束（载客 ≤ 5、载货 ≤ 4）；重量、体积字段可保留但算法不校验；不考虑优先级，所有订单平等 |
| Q4 | 时间窗 | 简化为"下单后半小时内能上车"；每半小时一个批次，批次开始前 5 分钟规划（如 7:55 规划 8:00–8:30 区间），规划后该区间停接新单；空载从 S0 出发，按欧氏距离估算行程时间；精确时间窗约束后续再迭代 |
| Q5 | 初始状态 | 仅支持静态闭环：全部车辆空载从场站出发、返回场站；不支持带初始位置和载量的增量规划；批次间不继承车辆状态 |
| Q6 | 批次锁定 vs 滚动窗口 | 批次锁定，半小时区间，不做滚动窗口 |
| Q7 | 单车 vs 多车 | 默认优先单车；单车无法满足时自动启用双车；车辆数由算法自动判定，无需编程组传入 |
| Q8 | ACO 参数管理 | 开放给编程组，经 `algorithmConfig` 传入，全部可选、不传用默认值；超建议范围返回 `warnings` 字段不拒绝请求；默认值随 Docker 镜像版本管理，镜像 CHANGELOG 记录参数变更。默认值：ant_count=30, max_iterations=100, alpha=1.0, beta=3.0, rho=0.1, Q=100, convergence_threshold=20 |
| Q9 | 规模上限 | 最大站点数 30、最大订单数 25（乘客+包裹合计）、最大车辆数 3、计算超时 10 秒；超限由业务侧拆分任务分别调用，算法侧不自动拆分 |
| Q10 | 无解与部分解 | 返回 HTTP 200，以 `status` 字段区分：`feasible` 完整解 / `infeasible` 无解并返回 `reason_code`（OVER_CAPACITY / TIMING_CONFLICT / PARTIAL_ONLY）；不返回失败订单列表和打折方案 |
| Q11 | 交付形态 | Docker 镜像（linux/amd64，基镜像 python:3.11-slim）；接口：`GET /health`、`GET /ready`（未就绪 503）、`POST /api/v1/plan`、`GET /api/v1/result/{requestId}`；站点坐标、订单数据均经请求体传入，不依赖挂载文件 |
| Q12 | 幂等/超时/重试 | `requestId` 幂等保留 24 小时，重复提交直接返回首次缓存结果（HTTP 200 + `cached: true`），不重新计算；计算超时 10 秒返回 HTTP 408 + requestId，可凭 requestId 轮询；轮询间隔建议 ≥ 2 秒；可重试：408、503、502、504；不可重试：400（参数校验失败）、422（业务不可行/无解）、413（规模超限） |
| Q13 | 输出字段 | 算法侧仅直接产出总里程 `total_distance`；预计耗时、载客/载货峰值、超载校验结果、乘客延误、预计收入、预计成本、综合评分均由编程组自行估算（算法组不持有定价模型与业务参数） |
| 附赠 | 场景 2 测试数据 | 已补齐：随更新版规范 PDF 提供，每组 3 名乘客 + 3 件派送 + 3 件揽收，标注为联调测试数据 |

## 回复后仍遗留的问题

1. **无解的 HTTP 状态码自相矛盾**：Q10 说无解返回 HTTP 200 + `status` 字段，Q12 却把 422 标注为"业务不可行/无解"。适配层需同时兼容两种返回，需算法组澄清以哪个为准。
2. **PARTIAL_ONLY 语义不清**：它被列为 `infeasible` 的原因码，但字面意思是"仅能完成部分订单"。部分成功时是否返回部分方案？（回复明确"不返回打折方案"，推测只给状态不给方案，待确认。）
3. **车辆数参数前后不一致**：规范文档把"启用车辆数量、多车并行模式"列为可调参数，回复（Q7）则说车辆数算法自定、无需传入。以回复为准，规范文档相关条目视为过期。
4. **高德路网获取进度**：直线距离只是过渡方案，路网数据由谁申请、何时到位、接入后算法改造周期，需要排期。
5. **镜像交付细节未闭环**：镜像签名、版本号与兼容规则、交付时间未在回复中覆盖。

## 回复对契约的影响（已落实到对接文档）

- 接口路径改为算法组实际交付形态：`POST /api/v1/plan` + `GET /api/v1/result/{requestId}`，废弃原 `planning-jobs` 三件套草案；仅保留 `requestId`，无独立 `jobId`。
- `rollingWindowMinutes` 废弃，改为半小时批次锁定模型；需求基线 P2 的"自动滚动调度"需重新定位。
- 快照输入大幅简化：车辆不再携带班次、位置、载量、ETA，仅提供可用车辆与容量；订单不带时间窗与优先级。
- 评分、延误、收入、成本等指标移出算法输出契约，由适配层基于计价规则与成本参数估算。
