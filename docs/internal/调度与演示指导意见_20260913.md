## 0. 一句话结论（先看这个）

死循环的根源不是算法"算不出来"，而是**演示成功耦合了三个易碎前提**：

1. **演示时刻必须落在公交班次的"运行窗口"里、且你手动选的「任务窗口」要早于班次发车**——否则"不折返"过滤会把订单整批丢掉（`DispatchServiceImpl.filterByNoBacktracking` + `buildVehicleWindows`）。
2. **算法服务必须在线且返回 feasible**——本平台算法是"失败即 `infeasible`、不静默降级"（`algorithm/app/solver.py:65`），任何一点覆盖不到就直接报错。
3. **13 个演示 SQL 必须按序跑齐、且真实公交线网数据存在**——否则挑车/拆段（多段联运）拿不到线路。

**破局出口（仓库里现成就有）**：`createManualPlan`（手工派单）**完全不走算法、不跑任务窗口/不折返过滤**，永远能产出一份可行方案。把"手工派单"作为保底闭环，"智能调度"只用来炫算法，演示就再也不会卡死。

## 一、仓库调度现状速览（我扫到的）

| 模块 | 文件 | 现状 |
|---|---|---|
| 一键智能调度主流程 | `yudao-module-transport/.../service/dispatch/DispatchServiceImpl.java`（`createSmartPlan`, L544-1051） | 已成体系：片区分批 → 选场站 → 选车 → 任务窗口 → 不折返 → 调算法 → 落库 + 多段联运拆段 |
| 自动挑车/挑场站规则 | `AutoDispatchPlanner.java` | 确定性纯函数；`selectAutoBatch` 只取"最新一单所在片区"；`selectVehiclesByLineCoverage` 一条线只出一辆车 |
| 公交骨架 + 货运绕行 | `algorithm/app/solver.py` + `passenger-cargo-dispatch.md` | 客运班次 = Mandatory Passenger Service，货运作绕行插入骨架间隙（与论文 Freight-on-Transit 范式一致） |
| 多段联运（换乘接力） | `MultiLegService` / `MultiLegPlanner` / `TransportLegDO` / `HandoverService` | **已实现**（09-11 审计报告说"缺失"已过时）——`createSmartPlan` 已调用 `multiLegService.planLegs(...)` 写运输段与交接 |
| 算法服务 | `algorithm/app/main.py`（`/api/v1/plan`） | 规模上限 **100 站 / 25 单 / 3 车**；`HACO-CPS 1.4.1`（混合蚁群+ALNS），失败即 `infeasible` |

| 拓扑可视化（不依赖算法） | `TransportTopologyServiceImpl` / `OrderTopologyRespVO` | 可单独展示"某单怎么分段、在哪站交接"，**不触发求解**，适合安全炫联运 |

## 二、你陷入死循环的根因（逐条诊断 + 代码定位）

### 根因 1：「任务窗口 / 不折返」对"当前时刻 vs 班次时刻表"极度敏感 —— 头号杀手

智能调度（`auto=true`）会算每台车"在任务窗口开始时已经开过哪几站"，**已经开过的站的取货单直接被丢弃**：

- `resolveTaskWindow`（L3492）：你不显式填 `windowStart/windowEnd` 时，窗口起点 = **当前时刻**（`currentBatch()`）。
- `buildVehicleWindows`（L3675）：用 `OperatingLineTimeline.at(lineStations, shift, at)` 算出窗口起点时车开到哪一站。**仅当窗口起点落在某班次的运行区间 `[plannedDepartureTime, +duration]` 内**才过滤"已开过"的站；否则整条线视为"都在前方"（安全）。
- `filterByNoBacktracking`（L3778）：取货站不在任何候选车"本窗口还会经过的站"集合 → 整单丢弃，报 `取货站已被车辆开过，不能掉头取货`。

**死循环场景**：你按 `docs/DEMO_GUIDE.md` 3.0 说的"现在 09:10 就选 08:00~10:00"，但 `demo-line346-orders.sql` 里 346 路的 `plannedDepartureTime` 若不是 08:00（比如 06:30 发、150 分钟跑完），那么窗口起点 08:00 时车已开过"中研所/邮电大学"等站 → TP346A/B/C 全被过滤 → 池里剩 0 单 → `DISPATCH_NO_BACKTRACKING` 报错。你改窗口、改顺序、重跑 SQL，反复横跳，正是这个坑。

### 根因 2：算法"3 车上限" vs 跨线联运批

- `MAX_ALGORITHM_VEHICLES = 3`（`main.py:48`；后端 `DispatchServiceImpl L155`）。
- `selectLineVehicles`（L3616）按 `neededRouteIdsByLegs`（L3565，从多段联运拆段推导需要的线路）每条线取 1 车，**封顶 3 辆**。
- 跨片区演示（沙坪坝：220 区间 + 318 + R104 = 3 线）刚好压线；若某批订单的拆段需要 >3 条线，多余线路无车 → 这些单无法分配 → 算法 `infeasible` 或 `unassigned`，演示崩。

### 根因 3：算法"失败即 infeasible，不静默降级"

- `algorithm/app/solver.py:65` 注释明确："HACO 模式本身不静默回落：无解/异常就返回 infeasible"。
- 后端 `createSmartPlan`（L821）：`STATUS_INFEASIBLE` → 抛 `DISPATCH_NO_FEASIBLE` + 原因码（`TIME_WINDOW_EXCEEDED` / `OVER_CAPACITY` / `DISTANCE_MATRIX_INCOMPLETE` …）。
- 任一原因码（路网矩阵缺、时长缺、超窗口、超容量）都会让整次一键演示直接失败——没有任何自动兜底到手工派单。

### 根因 4：演示数据顺序依赖 + 算法服务必须在线

- `docs/DEMO_GUIDE.md` 1.3 要求 13 个 SQL 严格按序执行；`demo-real-bus-shifts.sql` 提供班次时刻表（正是根因 1 的"敏感源"），`demo-line346-orders.sql` 提供 346 路班次。漏跑任一个，挑车/拆段/窗口计算都会拿不到数据。
- 算法服务宕机或 `ALGORITHM_BASE_URL` 不通 → `algorithmAdapter.plan()` 抛异常 → 任务置 FAILED，订单回池（P0-1 兜底做了释放，这点做得好，不会脏数据，但演示照样中断）。

## 三、给调度（算法 / 排班）的改进意见（结合论文）

你现有的"公交骨架 + 货运绕行 + 不折返 + 片区分批"范式，与文献 **Freight-on-Transit / Cargo Hitching（公交带货）**、**DRT 按关系模式分类（many-to-one）**、**ALNS / 蚁群—遗传混合**完全吻合，方向是对的。具体可落地的改进：

### 3.1 把"部分不可行"从 infeasible 改为 unassigned，交多段联运接力（最该改）
- 论文依据：客货邮本质是**分段联运（multi-leg relay）**，单条线覆盖不到的货自然该交给下一条线（日照慧城通、磐安 BRT 都是"公交带货 + 智能中转"）。
- 现状：算法一遇覆盖不全就整体 `infeasible`，等于剥夺了 `MultiLegService` 的价值。
- 建议：算法对"本批车辆覆盖不到的订单"返回 `unassigned_order_ids`（你们 `SolveOutcome` 已有该字段，`solver.py:44`），后端**不为整体失败**，而是把未分配单交给 `MultiLegPlanner` 走"跨线下一段"接力——这正好把根因 2/3 的崩溃转成一次正常的多段调度。

### 3.2 时间窗做鲁棒松弛（不确定性理论）
- 论文依据：农村场景到站时间、装卸时长高度不确定，应用**不确定性理论（uncertainty theory）做鲁棒调度**，时间窗适当放宽可显著降低无解率与成本。
- 建议：演示态/ rural 默认允许"取货站已开过但允许小折返（≤ θ 公里/分钟阈值）"，把根因 1 的硬过滤改成软惩罚；或至少把 `batch-minutes` 默认放宽到覆盖整条线（已是 480，够），并**在演示态默认关闭 no-backtracking 硬过滤**（加开关 `yudao.dispatch.no-backtracking=false` 演示用）。

### 3.3 双容量 / 行李舱拐点参数（来自文献可复用结论）
- 文献《文献检索报告》"总体研究格局与空白"给出：行李舱带货存在 **θ≈0.6 容量拐点**（超过后边际成本陡增）、**放宽时间窗可降成本**、**众包接力参与率 >40% 时送达时效 +34.2%**。
- 建议：把这些参数显式做成 `PricingRule` / 算法配置项，演示时可在"运营概览"展示"本趟捎带 X 件、利用率 θ%、较专车配送省 Y 元"——这正是老师最爱听的"降本增效"量化点（呼应菏泽/日照"5kg 仅 5 元"的普惠叙事）。

### 3.4 评估 KPI 对齐政策（答辩加分项）
- 文献给出 **福建德化 / 柘荣客货邮融合评估 KPI 集**；政策《交运发〔2023〕179号》给出县级中心—乡镇站—村点三级指标体系。
- 建议：把"县中心—乡镇站—村点三级覆盖率、日均捎带件量、降本率、准时率"做成演示大屏指标，直接对齐老师熟悉的官方考核口径（详见第四节案例锚点）。

## 四、给老师的演示样例（可成功配方）

### 4.1 总原则：两条不依赖算法的旁路打底，智能调度只炫不背锅

| 演示环节 | 用哪条路 | 会不会卡 |
|---|---|---|
| ① 用户小程序下单 → 后台看到单 | 正式接口 | 不会（不调算法） |
| ② 调度出方案 + 可视化 | **优先手工派单**（保底） | **不会**（绕过算法/窗口） |
| ③ 炫"算法智能排班" | 智能调度，**且窗口起点设在所有班次发车之前** | 基本不会（见 4.3） |
| ④ 炫"跨线联运/换乘接力" | **拓扑页 `TransportTopologyServiceImpl`**（不求解）或智能调度+窗口修复 | 不求解就不卡 |
| ⑤ 司机端执行 + 用户通知 | 正式接口 | 不会 |

### 4.2 保底闭环（100% 成功，5 分钟）

1. 小程序 `13800000000 / 123456` 登录 → 寄件 → 选"县城客运中心→青山镇站" → 提交。
2. 后台 `admin/admin123` → 运输管理 → 调度中心 → 勾选该单 → **归集入池** → 点 **手工派单**（手动选场站=县城客运中心、车辆=渝A·B5201、把单加进去）→ 生成。
3. 审核 → 下发 → 用对应司机手机号登录小程序司机端，看任务、装车/妥投；用户端看通知。
   - 这条路**完全不经过算法与任务窗口**，任何时刻、任何数据状态下都能跑通。先把这条练熟，演示就永远有底。

### 4.3 炫算法时的"必成功"前置（破解根因 1）

若想展示"一键智能调度"，**务必显式填写任务窗口，且让窗口起点早于所有演示班次的发车时间**：

- 在调度台工具栏把「任务窗口」设为例如 `05:00 ~ 22:00`（窗口起点 05:00 早于任何 demo 班次发车）。
- 为什么：窗口起点 05:00 < 班次 `plannedDepartureTime`（如 08:00）→ `buildVehicleWindows` 算得 `elapsed < 0` → 整条线视为"都在前方" → `filterByNoBacktracking` 一个单都不丢 → 算法拿到完整订单 → feasible。
- 批次只勾**同一片区**（如只勾 346 路走廊的 4 单），避免 >3 线触顶（根因 2）。
- 算法服务确认在线：`curl http://localhost:48080/admin-api/infra/health` 与 `docker compose logs algorithm` 无错。

### 4.4 跨线联运（换乘接力）的安全炫法

- **最稳**：后台"运输拓扑 / 订单拓扑"页，选 `重邮→重庆交通大学` 这种跨线单，直接展示 `MultiLegPlanner` 拆出的"347 路 邮电大学→南坪站 / 303 路 南坪站→七公里"两段 + 南坪站交接——**不触发求解**，必出图。
- **进阶（想看真实调度）**：用 4.3 的窗口前置法跑智能调度；若仍 `infeasible`，立刻回退到 4.2 手工派单 + 4.4 拓扑页，演示叙事不断。

### 4.5 答辩话术锚点（真实案例，老师认）

把你的平台对应到已落地的真实客货邮平台，老师一眼就信：

## 六、给下一步的最小动作建议（按性价比排序）

1. **加一个演示开关** `yudao.dispatch.no-backtracking`（默认 true，演示设 false）——一行配置根治根因 1，不用改任何逻辑。
2. **智能调度 infeasible 时自动提示"可改用手工派单"**（前端按钮直跳手工派单）——把死循环变成一次自然兜底。
3. **把 unassigned 交给 MultiLegPlanner 接力**（3.1）——让算法"部分不可行"也能出方案，联运价值真正落地。
4. **演示大屏加"降本/利用率 θ/准时率"指标**（3.3/3.4）——老师最买账的量化叙事。

> 以上 1–2 是"今天就能做、立刻止血"；3–4 是"一周内做完、答辩加分"。
