## 3. 要接入什么

### 3.1 真算法服务（唯一关键外部接入）

**现状**：平台侧一切就绪，对端是 mock。`mock-algorithm/README.md:11` 自述"不实现真实最短路或调度优化"；`.env.example:18` 指向 `http://mock-algorithm:8000`。真镜像（算法组 Q11 承诺：linux/amd64、四接口）未交付，遗留问题 1（无解返回 200 vs 422 矛盾）、2（PARTIAL_ONLY 语义）、5（镜像签名/版本/交付时间）未书面闭环（`docs/algorithm-doc-review.md:57-63`）。

**"接入完成"的定义（缺一不可）**：

1. 算法组交付镜像 + 版本号 + CHANGELOG + 书面交付日期；
2. 真服务通过契约验收测试（见 §5.6）：feasible / infeasible / 413 / 408 轮询 / 同 requestId 幂等重发 / `/health` `/ready`；
3. 遗留问题 1、2 书面结论落进契约文档；
4. 影子运行通过：同一批订单真算法方案与手工方案对比（总里程、车辆数、时序合规率）达标后，按场站灰度、全量；
5. 回退预案可演练：算法不可用时管理端手工派单兜底（链路已存在，需写进运维手册并实际演练一次）。

**切换工程步骤**：

1. 契约验收（挡住不合格镜像，不接进系统）；
2. 部署切换：compose 替换 mock 服务或算法组独立部署，仅改 `ALGORITHM_BASE_URL`，沿用 `127.0.0.1` 内网绑定，healthcheck 用 `/health` `/ready`，后端代码零改动；
3. 影子运行（真算法出方案但不下发，人工对比）；
4. 单场站灰度 → 全量；
5. mock 保留为 dev 联调与故障演练环境。

**必须前置处理的技术事项**：

- **`totalDistance` 单位版本化**（最隐蔽的坑）：当前契约下算法返回经纬度欧氏距离（"度"），`mock-algorithm/app/main.py:170` 可证。高德路网接入后返回值将变为真实公里。落库与展示逻辑必须按 `algorithmVersion` 区分单位，或推动算法组在响应中增加单位字段，并写进契约——否则路网切换日就是里程数据翻倍出错日。
- **超限语义二选一**：契约要求适配层"超限拆分+合并"（`docs/algorithm-integration.md:74` 责任 4），被回滚的 PR #63 选择了"预检报错、人工拆批"。需要产品层面裁定：实现自动拆分，或修改契约文档把该责任划掉。建议选后者（半小时批次天然限流，人工拆批可接受），保持文档与代码一致。
- **`scenario` 字段**（更正此前评审中的过度表述）：契约 `algorithm-api.yaml:193-197` 实际包含该字段并标注"仅供 Mock 测试，真实算法可忽略"。管理端 UI 未暴露它，生产请求中恒为 null，**无需改代码**；仅需在契约验收时增加一条用例：带 `scenario` 请求真服务，确认被忽略而非 400。
- **无解双形态**：`AlgorithmClient.toInfeasible`（`AlgorithmClient.java:118`）已兼容 200/422 两种返回，待算法组书面确认唯一形式后删除兜底分支。

### 3.2 高德路网（远期，与算法组协同）

直线距离是双方确认的过渡方案（`docs/algorithm-doc-review.md` Q1）。责任方（谁申请路网数据、何时到位、接入后算法改造周期）未定，需要排期。**对平台的影响集中在距离语义切换**，见 §3.1 单位版本化。平台自身无需提前写任何路网代码。

### 3.3 明确不需要接入的（防止过度工程）

- **车载 GPS 硬件**：当前"司机端上报优先 + 插值兜底"已满足监控与实时公交需求。除非监管合规要求，不主动接入。若未来接入：`DriverAppServiceImpl` 链路之外必须先补 WGS-84→GCJ-02 坐标转换（目前全仓库只有注释、没有实现，`AlgorithmStationDTO.java:9`），否则所有距离计算偏移百米级。
- 短信、微信小程序登录、百度地图 GL：均已完成接入，无欠账。

## 4. 要补全什么（按优先级）

### 4.1 【最大缺口】估算层：预计到达时刻 + 计价/收入/成本估算

**证据**：`insertPlanItems`（`DispatchServiceImpl.java:745-760`）落经停明细时从不写 `estimatedArrivalTime`；全仓库该字段只有两个读取方（`AppSendController.java:127` 包裹追踪、`DriverAppServiceImpl.java:285` 司机任务），**没有任何写入方**——小程序"预计到达"与司机端 ETA 是死功能。契约 Q13 明确算法组不产出耗时/收入/成本/评分，由编程组自估（`docs/algorithm-doc-review.md:54`）；适配层责任 6 同此（`docs/algorithm-integration.md:76`）。

**补全方案**：

1. 新增 `DispatchEstimationService`：按各车经停序列，用站点坐标 Haversine 距离 ÷ 平均时速（可配置，初始 25 km/h）逐站累计，写入每条 plan item 的 `estimatedArrivalTime`（含停站作业分钟数）。智能/手工派单两条路径都要调用。
2. 计价规则配置化：新增计价规则表（客运人公里价、货运件/公斤价、成本参数），走 `sql/incremental/` 人工迁移入口；管理端「系统基础设置」加维护页。
3. 方案估算摘要：方案落库时计算预计耗时、载客/载货峰值、预计收入、预计成本，存 `transport_dispatch_plan` 扩展列，管理端方案详情展示。
4. DoD：小程序追踪页与司机端任务列表展示真实 ETA；管理端方案详情有估算摘要；单测覆盖估算逻辑。

**工作量**：约 4–6 人日。这是 PR #63 用"实时位置 ETA"绕开、却从没真正解决的根因。

### 4.2 重新落地 PR #63 的有价值部分（修复版）

| 算法规模预检（30/25/3） | 原样恢复；与 §3.1 超限语义裁定保持一致 |

### 4.3 证照/保险到期预警（P1 欠账，小）

**现状**：司机档案已预留 `licenseExpireDate`（`DriverDO`），无任何预警逻辑；车辆保险到期字段缺失。
**方案**：车辆表补保险到期列（增量迁移）；定时任务（已有 `yudao-spring-boot-starter-job`）每日扫描 T-30/T-7 到期项，管理端预警列表 + 可选短信通知司机。
**工作量**：约 2 人日。DoD：到期司机/车辆在管理端预警页可见， Cron 有单测。

### 4.4 异常工单（P1 欠账，中）

**现状**：未启动；反馈（feedback）已落地可复用其模式。
**方案**：工单表（类型/来源订单或班次/状态机/处理人/SLA），管理端工单列表与处理流，小程序"我的"入口提异常；状态变更走审计日志（需求关键约束）。
**工作量**：约 4–5 人日。

### 4.5 财务结算中心（P1 欠账，大）

**现状**：`controller/admin/settlement/` 与 `service/settlement/` 仅 `package-info.java` 占位，前端 `views/transport/settlement/` 为空目录；注意与已实现的调度返程结算区分。
**方案**：营收统计（按订单类型/班次/线路聚合）、运营成本（依赖 §4.1 计价与成本参数）、对账结算（司机/班次维度结算单）。依赖 §4.1 估算层先行。
**工作量**：约 6–8 人日，建议拆分多个 PR。

### 4.6 契约验收测试基建（真镜像验收门禁）

**方案**：把 `mock-algorithm/tests/` 改造为可用环境变量 `ALGORITHM_BASE_URL` 指向任意实现的契约测试套件（新增 `scenario` 忽略性用例、幂等重发用例、408 轮询用例）；README 写明"真镜像验收 = 该套件全绿"。镜像到位当天即可执行验收，不用临时写。
**工作量**：约 1–2 人日。**这是阶段 B 的入口，必须先行。**
